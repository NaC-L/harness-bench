Repair `src/ledger.js` so local ledger commits survive an interrupted invocation or a transient filesystem error. Keep the exported `commitBatch(directory, batch, options)` and `recoverLedger(directory, options)` APIs. Do not modify tests or package.json; use no dependencies, services, network, timers, or subprocesses.

Contract:
- A batch is `{id, entries: [{key, delta}, ...]}`. IDs are nonempty strings. Keys match `/^[a-z][a-z0-9_-]*$/`; deltas and resulting balances must be safe integers. Empty batches are valid. Invalid batches reject with `error.code === 'ERR_INVALID_BATCH'` before changing durable data.
- A ledger snapshot is `{revision, balances, receipts}`. Initially it is `{revision: 0, balances: {}, receipts: []}`. Missing keys start at zero. Apply entries in order, increment revision once per distinct batch, and append `{id, entries}` to receipts. Repeated keys are allowed. Return the complete snapshot from both APIs.
- Reusing an ID with exactly the same ordered entries returns the existing snapshot without applying it again. Reusing it with different entries rejects with `ERR_BATCH_CONFLICT`, preserving committed data.
- `options.io` defaults to `node:fs/promises` and supplies its ordinary `mkdir`, `readFile`, `writeFile`, `rename`, and `unlink` methods. Do not silently retry or swallow I/O failures (except ENOENT for missing owned files). A method may fail before taking effect or after a partial staging-file write. The caller can retry with healthy I/O in a fresh invocation.
- Await `options.checkpoint(phase)` if supplied at `prepared`, `published`, and `complete`, in that order for a new successful batch. At `prepared`, the full intended transaction is durable enough for `recoverLedger` to finish it without the original caller/batch. At `published`, the final ledger snapshot is durably published. At `complete`, recovery metadata has been removed. A callback can throw to simulate interruption; propagate that exact error. At every boundary a fresh recovery/retry must converge to one application, never lose other batches or produce a balance/receipt mismatch.
- Recover an earlier pending transaction before processing a new one. Recovery is repeatable, returns the committed snapshot, and does not require callbacks. Unfinished staging files are not committed transactions. Do not remove unrelated files. Keep owned files local: `ledger.json`, `ledger.tmp`, `pending.json`, and `pending.tmp`. Invalid JSON in durable owned files rejects without silently resetting data.

Calls are sequential: concurrent writers, hostile edits of owned files, OS crashes/power-loss/fsync guarantees, and transient read failures during recovery are not part of this task. Recoverable failures include a staged-write failure, a failed rename, and a failed cleanup unlink. Temporary files may remain after a failure. The existing happy-path tests are intentionally sparse; preserve their behavior and implement the complete contract.
